# Governed Execution Profile

**状态：** 验收设计提案，2026-11-08 更新。本文不代表已实现 Profile、新 API、wire 契约或生产就绪。
当前行为以 API、[事件语义](events.md)和发布说明为准。

## 责任边界

本文是[Standard Embedding 与执行 Profile](execution-profiles.md)中的治理层次，增加集成义务，
不代表独立 Kernel 或新增 `agent.Profile`。

Core 执行已配置的授权、审批、工具和生命周期控制；集成方负责可信身份、委托、资源绑定、
持久业务效果与恢复。Policy hook 不是针对同进程恶意代码的隔离边界。

保留普通嵌入模式。先在参考集成中验证受治理部署契约，不为适配某个企业身份模型直接新增
Core 构造器或扩展 `policy.Action`。

源码中的[受治理工作区示例](https://github.com/axisvela/praxo-core/tree/main/examples/governed-workspace)
演示必要本地控制、绑定参数的单次审批和执行前策略复核。它不是通用 Core Profile、可信身份服务
或持久审批/效果存储，也不构成新的发布保证。

## 强制入口边界

当前 Go 有意允许 `Policy == nil`，并将空 `AllowedTools` 解释为不限制；保持 Standard Embedding
兼容行为。PRAXOVELA 等治理产品应提供强制装配入口，在模型调用、工具发现/暴露和工具执行前拒绝
缺失控制。校验失败不得回退普通 `agent.New`。这是产品要求，不是已实现的 Core 新构造器。

执行边界归可信装配层和工具服务所有，不能仅靠可选 Middleware 链。Middleware 不得删除必需检查、
替换可信身份或审批证据，或让实际操作偏离已授权操作而不重新授权。同进程不可信代码需要外部隔离/
执行边界；Go wrapper 本身不能约束恶意同进程代码。

| 配置或事件 | 当前 Standard Embedding | 治理集成要求 |
| --- | --- | --- |
| 缺少 Policy | 授权 helper 允许执行 | 启动时拒绝，在模型/工具访问之前失败 |
| 空 AllowedTools | 名称范围允许全部已注册工具 | 缺失范围应拒绝；显式区分允许集合、All 与 None |
| 必需策略服务不可用 | Hook 错误终止相关路径 | 保持 fail-closed，不允许宽松回退 |
| HITL 修改最终参数 | Core 对修改后操作重授权 | 另需绑定审批证据、最终操作、上下文、有效期与允许使用次数 |
| 操作期间撤销授权 | 不保证远程操作立即终止 | 实际 Effect PEP 执行提交时约束，由执行权威确认停止/结果 |

All/None 是设计上的范围选择，不是新增枚举或 Wire 变化。消费者必须在工具暴露和调用处执行。
尤其不能把 None 映射为当前的空 AllowedTools，否则实际会授予不限范围；显式 All 也不能绕过
每次受保护调用的 Policy。

## 统一装配设计

当前没有通用 Governed 总开关；Policy、范围、HITL、事件分别配置，消费者提供外部执行约束。
目标是一个可信装配入口、结构化配置和依赖校验，而不是用布尔值暗示外部保证。
先在明确消费者中通过既有接缝验证，不在此提议新增 `pkg/...` API。

入口必须在模型请求与工具暴露前校验，只返回受控运行入口，不向不可信调用者暴露可变安全选项
或未受保护的工具句柄。缺失控制、不支持必需能力或配置冲突时拒绝构建，不回退 `agent.New`。
这防止可信装配误配置，不隔离同进程恶意代码。

以下仅为消费者配置示意，不是已支持的文件格式、Core 选项或共享 Wire schema：

```yaml
execution:
  level: governed
scope:
  mode: allowlist
  tools: [robot.submit, robot.status, robot.cancel]
security:
  identity: required
  policy: required
  approval: required-for-sensitive-actions
effects:
  recovery: authoritative-query
  retry: guarded
evidence:
  before-effect: required
  after-effect-failure: reconcile
```

范围显式区分 `all`、`none`、`allowlist`；None 在暴露和调用两处执行，不能映射为空 AllowedTools。
验证者、策略、审批、效果与证据依赖由可信代码绑定；凭据和权限不能来自模型控制的配置。
选择层次只选择义务，不会创建缺失服务。

| 层次 | 执行责任 |
| --- | --- |
| 装配入口 | 必需依赖、显式范围、配置兼容、不宽松回退 |
| Core | 已配置授权、最终操作重授权、局部生命周期与取消 |
| 工具 / Effect PEP | 审批消费、最终绑定、资源约束与当前权限 |
| 执行权威 | 去重、权威状态、取消确认与 fencing |
| 部署 | 隔离，以及适用的受控停止和安全系统 |

装配校验不等于行为验收。逐项记录要求 ID、执行组件、配置结果、准确行为测试/产物和剩余缺口。
配置客户端不证明响应丢失恢复；启动检查不替代逐操作的过期、撤销和资源版本复核。
配置变更在使用前重新校验，排队工作仍须满足执行时约束。

## 受治理部署

| 要求 | 拒绝或验证条件 |
| --- | --- |
| 授权必需 | 缺失 Policy 时，在模型请求和工具执行前失败 |
| 工具范围明确 | 区分不限制、允许集合、全部禁止；不能把当前空 `AllowedTools` 当成全部禁止 |
| 安全上下文可信 | 在执行边界拒绝缺失、无效、过期或身份、租户、资源绑定不匹配的请求 |
| 最终操作绑定 | 授权与必要审批覆盖最终工具名和参数；修改后不能沿用不匹配的审批 |
| 依赖故障 | 必要身份校验、策略与执行前证据依赖故障不得静默放行 |
| 敏感效果 | 凭证、资源限制和审批要求在工具/服务边界执行，不能仅依赖提示词 |

### 验收清单

G1-G8 是稳定文档引用，不是 Core 符号或 Wire code。完整治理集成需逐项提供证据；审批等条件性
机制必须声明适用规则。必需检查跳过、阻塞、失败或未运行时，不满足验收。有理由的排除只能支持
缩小范围的实验，不构成完整 Profile 声明。

| ID | 义务与最低验收 |
| --- | --- |
| G1 | 可信强制装配在模型访问、工具发现/暴露和执行前拒绝缺失控制；测试其他入口、回退与校验后变更 |
| G2 | 暴露和调用均执行 All/None/allowlist；None 不允许工具，编辑不能扩大范围 |
| G3 | 可信身份、调用者/Agent、衰减委托、租户与资源绑定；按声明协议拒绝缺失、过期、重放或不匹配权限 |
| G4 | 最终操作与审批绑定、有效性、消费和撤销；测试编辑、排队延迟、并发单次消费与崩溃恢复 |
| G5 | 必需依赖和执行前证据失败拒绝新的依赖操作；实际边界执行凭据、资源约束与必需隔离 |
| G6 | 上下文信任贯穿装配、摘要、压缩、offload 与恢复；恶意数据不能获得指令权威或执行权限 |
| G7 | 稳定逻辑操作身份、受控重试、权威恢复、资源并发/fencing 与真实取消语义；测试响应丢失、旧 Checkpoint 与旧所有者 |
| G8 | 关联、脱敏证据及明确确认语义；分开执行前门禁、提交后修复与效果结果，保留失败尝试 |

每项适用 G 要求都包含允许路径、负向与故障测试。拒绝所有工作的实现不能仅凭未授权效果为零通过。
每个测试定义初始状态、注入点、有界等待、预期/实际效果及权威结果断言。

参数未变不等于授权永久有效。集成方必须定义过期、撤销、排队延迟和资源版本语义，
包括是否在业务提交时重新校验。单次执行前检查不能承诺即时撤销。

安全上下文试验应先复用已有适配器契约，明确签发/校验责任、调用者与 Agent 绑定、
委托衰减、租户/资源范围、有效期和决策关联。未经验证的 metadata 不是权限。
只有具备明确消费者、负向测试和兼容性复核后，才考虑共享契约。

## 上下文信任

当前 Go 的召回与 Skill 装配使用 System 消息。目标是明确区分部署方指令、经过批准的 Skill
指令和不可信检索/工具数据；实现了 Skill 接口本身不构成信任依据。

来源与信任差异必须在装配、摘要、压缩、offload 和恢复后保留。测试需要检查构造的上下文，
并以恶意 Memory、Skill 和工具结果尝试未授权效果。固定模型 fixture 用于确定性门禁；
真实模型攻击试验作为额外的版本化证据，不能作为确定性安全保证。

修改消息 role 或增加分隔符不是授权机制。默认 role 变化需要行为兼容性复核和明确迁移或
显式启用路径，不能因 API 快照未变就作为静默补丁发布。

源码中的受治理工作区示例包含显式上下文准入路径：批准 Skill 按摘要绑定，Memory/工具/摘要
作为数据封装，压缩保留来源，文本恢复从当前配置重建指令。它是示例契约，不是 Core API 或
通用 Prompt Injection 过滤器，也不认证来源身份或提供持久 lineage。

## 效果与恢复

### Governed Effect Boundary

此边界由产品与实际工具/业务服务实现，Core 提供授权、审批和执行钩子，不提供分布式事务或企业
执行服务。AEGIVELA 是可选策略/审批集成，独立消费者可以使用其他权威。

| 步骤 | 责任与必要行为 |
| --- | --- |
| 01 Intent | 消费者确定逻辑业务操作与目标资源，不仅是模型 tool-call ID |
| 02 Resolve Context | 可信验证者确认调用者/Agent 身份、委托、租户和资源范围；模型 metadata 不是权威 |
| 03 Authorize | 策略/审批权威评估操作与必需审批，依赖错误应拒绝 |
| 04 Prepare | Effect PEP 绑定最终工具/参数、上下文、审批引用和有效期、稳定业务幂等键及执行约束 |
| 05 Invoke | 受控工具/服务边界在实际操作前复核绑定与当前约束 |
| 06 Confirm Effect | 执行/业务权威区分确认成功、确认无效果与未知；传输错误或 Run 完成都不足以证明 |
| 07 Persist Evidence | 消费者保存结果、关联信息和恢复依据；证据失败不会抹去已提交效果 |
| 08 Reconcile | 查询权威状态、去重、按规则补偿或转人工，不盲目重试未知效果 |

这是责任流程，不是原子协议。若执行前要求持久意图或审批证据，其保存必须在 Authorize/Prepare
成为门禁，不能推迟到步骤 07；前置失败阻止 Invoke。提交后的证据失败应补证或对账，不应自动回滚
或伪报无效果。

审批证据需绑定已认证上下文、目标、最终参数、决策身份、有效区间与使用/重放语义。参数编辑、过期、
资源变化和排队执行均需定义复核。Core 对同参数重授权不等于已实现持久审批消费、撤销传播或目标端
提交约束。实际 Effect PEP 负责最终约束；本地 Run 取消不证明远程已接受的操作停止。

消费者明确把审批使用绑定到逻辑操作的并发仲裁点。两个 worker 不能把单次审批花在两个操作上。
定义预留/消费之后、调用之前崩溃，以及目标接受后、本地记录前崩溃的恢复规则。
相同操作重试不能意外消费第二份审批或产生第二次效果。测试这些窗口、并发消费、最终放行前撤销和
资源版本变化。这需要目标侧协议，不是新增 Core 分布式事务。

### 恢复语义

`tool.call` 表示意图，不证明执行或提交。Stream 投影、`run.completed`、Memory 写入和
Checkpoint 不构成事务；执行返回错误也不证明外部业务效果没有发生。

集成层需要区分意图、执行尝试、确认业务提交、拒绝/无效果和结果不确定。证据持久化是另一
维度：业务已提交时，证据可能尚未可靠保存。这些是设计上的区分，不是新增 Core 事件名或
强制 wire 枚举。

幂等键应对应稳定的逻辑业务操作并绑定请求内容。新生成的 run ID 或模型 tool-call ID
不自动适用。应定义保留期、参数不匹配拒绝、并发重试和权威状态查询方式。

查询本身不授权重试。落后副本、已过期幂等记录或仍在途请求对应的 `not found` 不证明无效果。
只有声明协议下的权威无效果证据，或有效保留窗口内的目标去重保证，才允许重试；否则保持未知、
对账或升级。测试原请求迟到、陈旧查询、键过期和并发重试。

| 故障 | 必要证据 |
| --- | --- |
| 策略或审批拒绝 | 业务效果为零 |
| 执行前崩溃 | 重试不会重复产生效果 |
| 提交成功但响应丢失 | 同一操作键的查询或重试能够找回原结果 |
| 提交成功但证据保存失败 | 对账或补证，不盲目重新执行 |
| Checkpoint 落后于效果 | 恢复先查询权威业务状态 |
| 目标无去重和状态查询 | 明确限制，转人工处理或定义补偿路径 |

不承诺通用 exactly-once。审计投递与业务提交需要明确的一致性机制，增加完成事件不能解决。
保留原始错误，通过明确诊断路径报告证据投递失败，避免递归发出失败事件。

补证只追加记录：保留原失败，记录修复时间、权威来源、操作关联与责任主体。
不得伪造原始观测时间，也不得用后续成功覆盖失败尝试。补证不是盲目重做效果。

## 证据与晋级

按[Execution Correctness Suite 提案](../project/execution-correctness.md)组织失败场景，
Core 机制、实际执行约束和运行结果分别提供证据。

当前只有部分证据：四种发布语言消费者测试覆盖应用拒绝缺失 Policy/范围、最终参数和审批编辑
重授权、策略服务错误；身份与长时配方覆盖选定应用 fixture。它们不验证产品强制入口不可绕过、
生产身份/委托、持久审批有效性或真实 Effect PEP 的撤销约束。这些仍属消费者验收门槛，
不能因本文存在就声明已完成。

遵循[测试证据规范](../contributing/test-evidence.md)，将声明关联到准确的 Core/adapter
版本、实际场景、断言、产物和剩余缺口。历史本地运行、当前自动化、独立复现和生产观察分别记录。

先验证集成契约和失败测试；晋级 API/wire 时履行兼容性政策、适用的 `spec/`、语言 parity、
一致性向量与消费者验证要求。发布本设计不改变运行时、schema 或语言支持承诺。
